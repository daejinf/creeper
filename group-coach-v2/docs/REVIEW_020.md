### 마지막 NEEDS_INPUT은 무엇인가요?

1명 모임에서 공동 제안은 메인·상세·일정 화면과 통합 점검을 모두 본인에게 배정했지만, 모의 개인 확인은 ‘메인 화면의 담당 결과물’만 포함했습니다. 개인 모듈은 범위를 넓혀 확정하지 않고 **공동 배정을 줄일지 / 개인 범위를 넓혀 확인할지** 요청했습니다. 새 개인 계획과 평가 기준은 저장·공유하지 않았습니다. 이 정상적인 확인 대기를 API 실패로 집계하지 않았습니다.

## 실제로 고친 문제

| 발견 문제 | 수정과 확인 |
|---|---|
| 잘못된 사용량의 소수·bool 값이 정수로 잘림 | 비정상 카운터를 INVALID_JSON으로 구별하고 전송을 반복하지 않는 검사 추가 |
| 공동 800자·12~16줄, 개인 2~4문장 강제 | 제거. 기존 reply 유지, summary와 details 기본값 추가. 상세 분석을 잘라내지 않음 |
| 주말 선호를 평일 불가로 처리 | preferred_times는 선호. available_weekdays만 확인된 엄격한 조건. 모델 추론은 SUGGESTED로 유지 |
| 개인 조건을 계획 생성 중 다시 추출해 근거 손상 | 확인 state는 코드 소유. 실제 본인 메시지 근거 검사, 새 본인 발언도 PLAN 입력에서 보존 |
| ‘직접 지정’ VALUE/null 버튼 때문에 상담 전체 실패 | 값 없는 버튼만 제거하고 실제 답변·질문·UNKNOWN 상태 보존. 직접 입력은 화면에 계속 제공 |
| 개인 요청에 승인된 본인 작업이 없음 | assigned_tasks 전달. 다른 사람 작업은 요청 검증에서 거부. 승인 범위 충돌은 NEEDS_INPUT |
| 공동 초안 예상 시간이 개인의 확정 시간처럼 작용 | 경험·진척·예산으로 개인 시간을 재산정. 범위·완료 기준과 확인 예산은 보존 |
| 보정 응답이 사용자에게 ‘JSON/의존성만 고쳤다’고 설명 | 내부 보정 대신 원래 코칭·계획 요청에 대한 완성 답변을 반환하도록 지침 수정 |
| 후속 작업이 선행 작업보다 먼저 끝남 | 날짜 순서 검사 추가. 순환·알 수 없는 의존 ID도 계속 거부 |
| 공동 점검 작업의 담당자가 null | 책임 구성원을 추천하고 투표받도록 수정. 최신 검증기는 미지정 담당자를 거부 |
| 현재 개인 계획을 생성 시각으로 추정 | current_plan_id와 소유자 FK. 과거 수정/실행 이벤트로 확실하게 연결되는 것만 복원 |
| 공동 평가 기준 없음·ID 연결 제약 부족 | GROUP/PERSONAL 불변 기준, 승인 포인터·개인 상태·과제 JSON 소유자/ID 제약 추가 |

기존 200개 예제는 모두 현재 GroupRequest 계약으로 읽혔습니다(데이터 검사, LIVE 품질 검증과 별도).

최신 검증기로 과거 결과를 다시 읽었을 때 1차의 계획 결과 25개 중 3개, 2차 25개 중 3개에 담당 미지정 또는 의존 일정 문제가 있었습니다. **3차 최종 계획 결과 34개는 모두 통과**했습니다. 계획이 없는 정상 확인 대기는 이 34개에 넣지 않았습니다. 이전 원본과 실패 이력은 삭제하지 않았습니다.

## DB 검증

- 신규 사용자 ID는 SW의 external_user_id로만 연결합니다. 동명 사용자·동일 사용자 다중 모임·개인 범위 분리를 검사했습니다.
- 1·3·5·8명 모임, 동시 투표·중복 동작, 한 사람의 실패, 입력 변경 중 결과 도착을 검사했습니다.
- 실제 PostgreSQL과 별도 Python 프로세스로 실행 소유권, 커밋 실패 후 암호화 응답의 저장만 재시도, 프로세스 종료 후 UNKNOWN 보존을 검사했습니다. 네트워크 대기 중 DB 잠금을 유지하지 않습니다.
- 현재 평가 모임의 **66개 구성원 범위 조회**, **68개 기준·계획·과제 조합 조회**를 확인했습니다. Python reader와 HTTP는 같은 구현을 사용합니다.
- 새 DB에 전체 마이그레이션을 적용한 결과 **15개 테이블·56개 제약**, 설치 성공. 격리 설치 DB는 제거했습니다.
- 실제 백업을 격리 DB로 복원하여 원본 스냅샷과 **내용 해시 일치**, 고아 과제 0건을 확인했습니다. 복원 시험 DB만 제거했으며 PostgreSQL 클러스터를 중단하지 않았습니다.
- 최종 감사: 고아 목표/과제/기준, 현재 공동 기준 누락, 과제 소유자 JSON 불일치 모두 **0건**.
- 미연결 구성원 **2,030개**는 과거·익명 시험 자료를 포함한 DB 행 개수이며 실사용자 수가 아닙니다. 연결 근거가 없어 닉네임으로 합치지 않았습니다. 미연결 ID에 후속 조회 권한을 부여하지 않습니다.
- 기존 프로젝트 핵심 소스 **60개 파일 해시 변경 0건**, 기존 wemeet_goals DB 내용 해시 일치를 확인했습니다. 이번 작업에서 기존 사용자 기록은 외부 모델로 보내지 않았습니다.

## 설치·화면·키

새 가상환경에 0.2.0 wheel과 선언된 기본 의존성만 설치했습니다. FastAPI·SQLAlchemy·기존 wemeet_ai가 없는 상태에서 import와 examples/core.py --check를 통과했습니다. 이후 선택 DB 의존성만 설치해 wheel의 reader로 실제 기준을 조회하는 SW 예제도 통과했습니다(AI 호출 없음). 배포 wheel의 Python 파일은 최종 소스와 일치합니다.

브라우저에서는 새 익명 3인 모임 생성 → 발언 저장 → 실제 COACH → 네 영역 요약 → 상세 펼침을 확인했습니다. 이 UI 연기 시험은 100개 평가와 별도이며 **HTTP 1회 / 2,510토큰 / 11,573ms**입니다. 개인 전체 UI 흐름과 4개 화면 너비 검사를 이번 검토에서 모두 수행한 것으로 표시하지 않습니다. 앞선 브라우저 승인 한도 오류는 이후 재실행되어 이 범위가 확인됐습니다.

공개 소스·문서·예제·평가 자료·wheel의 실제 설정 비밀값 일치 검사에서 노출이 없었습니다. 키/전체 DB 주소/복구 키는 출력·전달하지 않습니다. 백업·원본 실행 추적·개인 자료는 Git에서 제외한 runtime에 보관합니다.

성공한 단계를 모두 다시 호출하지 않았으므로 최종 결과에는 회차 내 여러 프롬프트 버전이 있습니다. **최종 단일 프롬프트로 전체 세트를 다시 실행한 점수라는 뜻은 아닙니다.** 변경된 단계만 새 버전으로 재검사했고, 이전 결과·소스 해시·사용량을 보존했습니다. 평가 실행기에서 새 시험 모임에 이전 메시지 ID를 재사용해 DB가 거부한 경우도 원본에 남아 있으며, 모임별 시험 ID를 분리해 재개했습니다. 이 경우 AI 호출 전에 거부됐습니다.

## 정리한 파일과 남은 범위

중복 실행기 tools/live_verify.py는 공통 평가 실행기로 대체하고 참조가 없음을 확인한 뒤 삭제했습니다. 구버전 0.1.2 wheel, 중복 build·pytest 캐시, 설치 검증용 일시 가상환경도 제거했습니다. DB·사용자 대화·마이그레이션·실패 재현 테스트·백업·복구 기록과 과거 평가 근거는 보존했습니다.

기술 기준은 통과했지만 아직 **SW팀의 직접 연결 확인, 사람의 의미적 품질 검토, 개인 전체 브라우저 흐름/반응형 검증**이 남아 있습니다. 공개 문장의 민감한 사유를 모든 표현 변형까지 코드가 완벽하게 탐지한다고 보장하지 않습니다. 개인 공개 요약은 본인 검토 후 공유해야 합니다. 초급자의 실제 수행 속도도 실제 사용자 평가가 필요합니다. 발견된 중대 결함을 숨긴 채 운영 인수 완료로 표시하지 않습니다.
