## 2. 단계 게이트

GATE A (승인 완료, 2026-11-18):

- 현재 HTML 9개를 LOCKED 디자인 기준으로 승인: 승인(D-A6)
- Timely LIVE 테스트 허용과 0B 호출 예산: 승인(D-A7, 0B 최대 12회)

에이전트가 추천 기본값을 정하고 근거를 기록하는 결정 (PROPOSED, 사용자 승인 대상 아님):

| 항목 | 추천 기본값 | 근거 | 전환 조건 |
|---|---|---|---|
| 계정·비밀번호 복구 | 복구 기능 없이 시작 | 이메일 필드가 없고 외부 계정이 필요 없음 | 이메일/SMS 등 외부 계정이 필요하면 사용자 승인 항목으로 전환 |
| 초대코드 | 서버가 난수로 만든 숫자 코드, `ACTIVE` 전환 때 폐기, 재발급은 그룹장만 | 원본은 숫자 코드 입력 UI이고 D-A5가 폐기·재발급 방향을 정함. 만료 시간은 2단계에서 정해 이 표에 기록 | 개인정보 범위 확대 시 |
| 최초 그룹장, ProjectBrief 수정 권한 | 생성자가 그룹장이고 ProjectBrief는 그룹장만 수정하며 revision마다 저장 | D-A5의 `그룹 생성하기`(그룹장만) 흐름 | 권한 확대 시 |
| Windows PostgreSQL 실행 방식, 테스트 DB | 0B-1에서 설치 상태를 확인한 뒤 정함 | 기술 검증 사항 | 새 주요 인프라 의존성이 필요하면 승인 |

GATE B — 3·4단계 전 (OPEN):

- 인터뷰 필수 항목, 최대 턴과 종료 조건
- moim-chat 상태 전환 방식
- private 정보에서 역할·투두 초안에 사용할 수 있는 필드
- 1·2·3순위 역할 배정의 미제출자 처리, 활성화 뒤 신규 합류와 재배정 규칙, 남은 역할이 없을 때의 중복 허용. 배정 시점(활성화 cohort 전원 제출 뒤 서버 1회 실행)과 순위별 충돌·순위 소진 뒤의 무작위 배정 원칙은 승인됨(D-A5)
- ProjectBrief 기반 그룹별 역할 후보의 생성 주체·시점·개수·표시 위치, source ProjectBrief를 가진 공용 candidate revision, 실패·재시도·STALE 규칙과 별도 LIVE 예산(포지션 등록 화면은 만들지 않음, D-A5)
- 사용자가 수정할 수 있는 투두 범위와 서버 역할 재배정 operation. 배정 역할·담당자 직접 수정은 허용하지 않음
- 배정 안내 문구에서 다른 구성원의 이름·순위를 보여줄지. 원본 `moim-chat` 데모 문구는 이를 노출하므로 순위 비공개를 유지하려면 문구 변경이 제품 차이로 승인돼야 함
- 역할·투두의 사용자 확정과 그룹 공개 범위
- ProjectBrief 변경 시 역할·투두 재검토 규칙

GATE D — 5·6단계 전 (OPEN):

- M2.review가 사용할 투두·결과물·숨겨진 평가 기준·첨부 범위와 사용자 이의 제기
- 기존 `up-msg`와 팀원 완료 기록을 활용한 M2 결과 표시 위치·문구
- M2 활성 시 `첨부하면 이 할 일을 완료로 표시` 체크박스의 의미와 PASS의 완료 반영 방식
- 이미지·PDF·DOCX 허용 범위
- 첨부파일 보관과 삭제
- 그룹 탈퇴와 계정 삭제 정책

GATE A에서도 코드 확인 없이는 결정하기 어려운 CSP 세부값, 상태 조회 주기와 스트리밍 지원을 사용자에게 추측으로 확정하게 하지 않는다. 0B에서 검증 결과와 추천안을 기록하고, 개인정보·비용·주요 의존성에 영향을 줄 때만 추가 승인을 요청한다.

## 3. 단계별 로드맵

0A-1 조사와 기준 제안 — 완료. 0A-2 운영 문서 생성 — 완료.

0B-1 저장소·환경·테스트 기반
- Git, 줄바꿈 보호와 clone 해시 검증
- Python·PostgreSQL·pyproject·Alembic·tests 구성
- 필요한 크리퍼 설정과 테스트 패턴만 선별 이식. 이때 크리퍼 기존 테스트를 실행해 `docs/ARCHITECTURE.md`의 모듈 판정을 다시 확인
- 원본 해시 검사와 결정적 테스트 실행 기반 구성

0B-2 M0 안정화와 LIVE 연결
- provider.request/response/json.parsed 원문 로그 제거, 자동 재호출 제거, 실패 시 오류 저장과 호출 로그 한 줄
- 승인된 범위에서 Timely LIVE 연결·구조화 응답·복구 경로 검증

0B-3 비동기 작업과 화면 캡처 기반
- FastAPI 백그라운드 작업과 DB 상태 테이블, 상태 조회와 새로고침 복구 기반 구성
- 원본·구현 화면을 1440×900으로 나란히 캡처하는 Playwright 스크립트 구성(픽셀 자동 비교 없음)

1단계 — 인증
- 회원가입, 중복 확인, 로그인·로그아웃과 서버 세션
- 승인된 비밀번호 복구 정책
- 실제 오류·로딩 상태와 인증 보안 테스트
- landing 템플릿 이식과 CTA 연결(로그아웃 → 로그인 → dashboard, 로그인 → dashboard)

2단계 — 대시보드·그룹·ProjectBrief
- 내 그룹 목록, dashboard/group 구현본의 `새 그룹 만들기` POST에서만 `FORMING` 초대방·최초 그룹장·서버 생성 초대코드를 만들거나 본인 소유 활성 초대방 하나를 재사용. 일반 GET·참여 화면 조회는 상태를 바꾸지 않음
- 초대코드 참여와 활성화 전 대기 상태(활성화 전 chat·그룹 실행 화면 접근 차단), 동일 그룹 코드 재발급, 빈 초대방 `CANCELLED`와 참여자가 있는 초대방 자동 폐기 차단
- 생성자 포함 최소 2명에서 `그룹 생성하기`(그룹장만) → `FORMING`을 유지한 채 `moim-group-create` 이동 → ProjectBrief 다음 버튼에서 revision 1 저장·활성화 cohort 고정·`FORMING → ACTIVE` 원자 전환·기존 초대코드 폐기 → 각자의 `moim-chat`
- GATE B 승인 전 ACTIVE 그룹 참여는 `GROUP_NOT_JOINABLE`로 차단
- 루트 원본은 보존하고 구현본에서 `moim-group-create-position.html` 이동과 완료 팝업을 이식하지 않으며 포지션 등록 화면·AI 인터뷰 시작 버튼을 만들지 않음
- ProjectBrief 저장과 버전
- ProjectBrief를 근거로 한 AI 팀 목표 표시문 생성·상태·revision
- 그룹·멤버 인가

3단계 — 개인 AI 인터뷰와 역할 순위 제출
- 개인 전용 대화와 MemberState
- GATE B에서 승인한 별도 LIVE 예산과 방식으로 ProjectBrief 기반 그룹 역할 후보를 한 번 생성해 공용 candidate revision으로 저장·복구
- 동일 candidate revision의 역할 후보 표시와 서로 다른 1·2·3순위 제출(후보 밖 문자열·중복·누락·stale revision 거부)
- 제출 뒤 `WAITING_ASSIGNMENT`, 순위 원문 비공개. 역할 배정·투두는 만들지 않음
- 비동기 실행과 새로고침 복구
- 다른 사용자에게 노출되지 않는 테스트

4단계 — 역할 배정·개인 투두 초안과 확정
- 활성화 cohort 전원 제출 뒤 서버가 1·2·3순위 순서로 한 번 배정하고, 같은 순위 충돌과 3순위 소진 뒤에만 서버 무작위 사용(AI 선택·재추첨 없음), 결과를 하나의 assignment revision으로 고정
- 최종 배정표 전체와 ProjectBrief로 팀 결과물 중복·누락을 검사한 뒤 private MemberState와 배정 역할로 개인 투두 초안 생성
- 기존 moim-chat의 투두 수정·직접 추가·삭제·확정 흐름을 실제 서버와 DB에 연결하되 배정 역할·담당자 직접 수정은 금지하고 승인된 서버 재배정만 새 assignment revision으로 처리
- 각 투두에 화면에 노출하지 않는 결과물·완료 기준·허용 증거를 함께 생성하고 투두 확정 시 같은 revision으로 고정
- 사용자 확정 전 private, 확정 뒤 필요한 역할·투두만 그룹에 공개
- 기간·업무량·담당자·ProjectBrief revision 검증

5단계 — 실행과 투두별 M2 평가
- 실제 진행률, 일정, 투두와 활동 기록
- 각 투두에 결과물 첨부
- M2가 해당 투두의 숨겨진 결과물·평가 기준으로 첨부 자료를 기준별 검토·평가
- GATE D에서 승인된 위치와 방식으로 PASS/재검토/추가 입력 상태, 완료 반영과 사용자 이의 제기 제공

6단계 — 마이페이지와 계정 생명주기
- 기존 디자인에 존재하는 사용자 정보와 설정
- 비밀번호 변경, 그룹 탈퇴와 계정 탈퇴
- 승인된 삭제·익명화·보관 정책

7단계 — 운영 준비 (실제 배포를 결정할 때만 수행. MVP 완료 조건이 아님)
- RLS 필요성 검토
- TLS, 비밀 관리와 암호화 백업
- 복구 리허설, 악성 파일 검사, 모니터링과 경보
- ASVS 기반 검토와 충분한 표본의 성능·비용 보고

한 번에 여러 제품 단계를 구현하지 않는다. 그러나 같은 단계 안의 가역적인 구현과 테스트를 위해 매번 승인을 요청하지 않는다.

## 4. 단계 완료와 보고

해당 단계에 실제로 적용되는 조건만 활성화한다.

공통 완료 조건:

- 운영 하드코딩이나 임시 우회 없이 실제 서버·DB 상태를 사용한다.
- 정상, 빈 상태, 로딩, 오류와 새로고침 복구를 필요한 범위에서 검증한다.
- 인증·인가와 개인정보 경계를 검증한다.
- 관련 결정적 테스트가 통과한다.
- 원본 HTML 해시가 LOCKED 기준과 동일하다.
- 문서와 HANDOFF가 현재 구현과 일치한다.

AI 기능이 생긴 단계부터:

- 승인된 LIVE 테스트가 통과하거나 정확한 BLOCKED 이유가 있다.
- 모델, latency, usage, 오류와 호출 횟수를 기록한다.

디자인 구현이 생긴 단계부터:

- 1440×900 스크린샷 캡처를 실행했고 사용자가 원본과 나란히 확인했다.

보고 형식:

1. 결과
2. 검증: 테스트, 보안, 디자인, LIVE 호출
3. 기존 전제와 달랐던 사실
4. OPEN 또는 BLOCKED
5. 다음 한 단계

빈 항목을 장황하게 채우지 않는다.

## 5. OPEN 요약

제품 OPEN은 `docs/PRODUCT.md` 5절, 위 GATE B·GATE D 목록, 보관·삭제는 `docs/SECURITY.md` 3절에 있다. BLOCKED 항목은 현재 없다.
