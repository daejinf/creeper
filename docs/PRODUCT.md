## 4. 디자인 검증 규칙 (운영 규칙, bootstrap §3 이관)

승인 전에도 원본을 수정하거나 과거 상태라고 추측해 되돌리지 않는다. 승인 후에는 각 단계 종료 시 해시가 위 기준표와 동일한지 검사한다.

화면 확인(스크린샷 나란히 비교):

- 픽셀 단위 자동 비교, 기준 이미지, 픽셀 허용 오차와 날짜·폰트 고정은 MVP 범위에서 하지 않는다.
- Playwright 스크립트 하나로 원본 HTML과 구현 화면을 1440×900 데스크톱 viewport에서 캡처해 나란히 저장한다.
- 원본과 구현 화면에 같은 개발 seed를 적용해 비교하기 쉽게 한다.
- 단계 종료 시 이 캡처를 실행하고, 사용자가 원본과 나란히 눈으로 확인한다.
- 캡처는 자동 합격·불합격 판정을 하지 않는다.

구현 화면 차이 분류:

- 데이터 차이: 실제 데이터 길이와 값 때문에 발생하는 차이
- 상태 차이: 접근성, 오류, 빈 상태와 로딩 때문에 발생하는 최소 DOM 차이
- 제품 차이: 정보 구조, 문구 또는 상호작용을 바꾸는 차이

원본 파일은 어떤 경우에도 직접 수정하지 않는다. 제품 차이는 사전 승인이 필요하다. 데이터·상태 차이는 시각 영향을 기록하고 스크린샷 확인을 거쳐 구현할 수 있다.

moim-chat.html은 2열 구조를 유지한다. 왼쪽은 개인 AI 대화, 오른쪽은 인터뷰 상태 또는 역할·개인 투두의 검토 영역으로 사용한다. 상태는 `INTERVIEW`(인터뷰·순위 미제출) → `WAITING_ASSIGNMENT`(제출 완료, 다른 팀원 대기와 서버 배정 실행 중) → `ROLE_TODOS`(배정 완료, 내 역할과 투두 초안) 순서로만 바뀌며 이 순서는 승인됨(D-A5)이다. 서버 상태가 바뀌면 접속 중 사용자는 상태 조회로, 미접속 사용자는 재접속 때 다음 화면을 본다. 역할 배정 전에는 오른쪽 투두 영역을 비우고 안내만 표시한다. 각 상태의 세부 문구·집계 표시 범위는 GATE B에서 결정한다.

왼쪽 대화와 오른쪽 패널은 서로 다른 임시 상태를 갖지 않는다. 둘 다 같은 서버 측 상태와 revision을 사용하며, 한쪽의 변경은 저장 성공 뒤 다른 쪽에 반영한다.

팀 목표 표시(`moim-group-create` 안내문, `moim-chat`의 "우리 팀의 최종 목표" 박스, `moim-group` 머리)의 생성·저장·실패 규칙은 `docs/ARCHITECTURE.md`의 `팀 목표 표시문`을 따른다.

## 5. OPEN 항목 (제품)

`docs/ROADMAP.md`의 OPEN 표와 함께 본다. 확정된 사실처럼 취급하지 않는다.

| 항목 | 상태 | 비고 |
|---|---|---|
| `moim-mypage`의 이메일 표시 | OPEN | `moim-signup`에 이메일 입력이 없다. 필드를 추가하면 제품 차이, 제거하면 디자인 변경이므로 1·6단계 전에 승인 필요 |
| `login-keep`(로그인 유지), `su-noti`(알림) | OPEN | 받쳐 주는 정책이 없다. 1단계에서 처리 방식을 정하고, 화면 변경이 필요하면 제품 차이 승인 |
| GATE B 항목 | OPEN | 인터뷰 항목·턴, 순위 미제출·신규 합류·재배정, 역할 후보 생성, 안내 문구의 타 구성원 정보 노출 등(`docs/ROADMAP.md`) |
| GATE D 항목 | OPEN | M2 결과 표시, 첨부 범위·보관·삭제, 탈퇴·계정 삭제 정책 |
