### D-B1 (2026-11-18) — GATE B 인터뷰·역할 후보·배정·투두 공개 정책

- 영향 단계: 3, 4, GATE D(확정 투두 표시), 5(그룹 화면 렌더링). D-A5의 순서(`INTERVIEW → WAITING_ASSIGNMENT → ROLE_TODOS`, cohort 전원 제출 뒤 서버 1회 배정, 순위 우선·충돌·소진 때만 서버 무작위)는 그대로이며 다시 정하지 않았다.
- 결정 (에이전트 추천안 B1~B9를 그대로 승인):
  - **B1 인터뷰:** 필수 4개(`weekly_available_minutes`, `current_level`, `scope`, `constraints`("없음" 허용)), 선택 4개(`current_progress`, `tools`, `preferred_times`, `support_needed`)는 한 번만 묻고 건너뛰기 허용. 최대 8턴, 필수 4개가 채워지면 종료. 순위 제출은 후보 확인 뒤 별도 버튼이며, 승인된 candidate revision이 없으면 제출 단계로 가지 않는다. 재개는 서버 저장 대화·MemberState에서 이어가고 순위는 제출 전까지 수정 가능.
  - **B2 chat 상태 문구:** 4개 화면 상태를 기존 2열 구조·스타일로 표시. ① 순위 미제출: 오른쪽 안내 "역할이 정해지면 여기에 내 투두가 만들어져요."와 비활성 `투두 확정하기`·`+ 직접 추가하기`. ② 제출 뒤 대기: "순위를 제출했어요. 다른 팀원을 기다리고 있어요"와 `N/M명 제출 완료`. ③ 서버 배정 중: "역할을 배정하고 있어요". ④ 배정 완료: `rolebox`의 내 역할과 투두 초안. 오류는 기존 `.msg err`와 다시 시도. 집계는 제출 수/cohort 수만 모든 구성원(그룹장 포함)에게 보이고 누가 냈는지는 보이지 않는다(개인정보 범위의 승인된 작은 확대).
  - **B3 공급자 입력:** 투두 초안에는 ProjectBrief, 내 배정 역할, 이름 없는 최종 배정표, `weekly_available_minutes`·`current_level`·`scope`·`preferred_times`·`tools`만 보낸다. `constraints`·private notes·순위 원문·대화 원문 전체·타 구성원 MemberState·이름·아이디·`user_id`는 보내지 않는다. 후보 생성은 ProjectBrief만 쓴다. 순위 검증은 서버 코드가 한다.
  - **B4 미제출·합류·재배정·중복:** 미제출자는 영구 대기(자동·강제 배정, 그룹장 제외 진행 없음). 활성화 뒤 신규 합류는 계속 차단(`GROUP_NOT_JOINABLE`). 재배정은 그룹장 요청 + 대상자 본인 동의가 있을 때만 같은 입력으로 새 assignment revision을 만들고 기존 draft·confirmed·숨겨진 기준을 STALE 처리. 중복 역할은 역할 수 < 인원일 때만 허용하고 구성원별로 결과물을 분할하며 팀 전체 deliverable coverage를 서버 코드로 먼저 검사. 서버 무작위는 감사 기록을 남기되 운영에서 고정 seed를 쓰지 않는다.
  - **B5 역할 후보:** ACTIVE 직후 서버가 ProjectBrief revision당 Timely를 1회 호출해 `source_project_brief_revision`을 가진 immutable candidate revision을 만든다(3~8개, 인원수 이상, 이름 ≤12자·짧은 설명). 모든 cohort 구성원이 같은 revision을 대화 칩·목록으로 본다. 개인·새로고침마다 재생성하지 않는다. 최초 생성과 사용자 명시적 재시도를 모두 D-A8에 따라 기록(고정 상한 없음). 실패는 오류와 다시 시도로 표시하고 고정 목록으로 대체하지 않으며 같은 `operation_id`는 멱등. ProjectBrief revision이 바뀌면 이전 candidate와 미제출 순위는 STALE이고 새 revision을 만든다.
  - **B6 배정 안내:** 다른 구성원의 이름·순위를 보여주지 않는다. 라운드별 일반 문구와 내 최종 결과(몇 순위로 배정됐는지)만 표시. **원본 `moim-chat` 데모 문구와 다른 제품 차이로 승인한다.**

### D-B2 (2026-11-19) — 인터뷰 진행 방식·chat 패널 문구·버튼 답변 (D-B1 B1·B2 보정)

## 4. 디자인 검증 규칙 (운영 규칙, bootstrap §3 이관)

승인 전에도 원본을 수정하거나 과거 상태라고 추측해 되돌리지 않는다. 승인 후에는 각 단계 종료 시 해시가 위 기준표와 동일한지 검사한다.

화면 확인(스크린샷 나란히 비교):

- 픽셀 단위 자동 비교, 기준 이미지, 픽셀 허용 오차와 날짜·폰트 고정은 MVP 범위에서 하지 않는다.
- Playwright 스크립트 하나로 원본 HTML과 구현 화면을 1440×900 데스크톱 viewport에서 캡처해 나란히 저장한다.
- 원본과 구현 화면에 같은 개발 seed를 적용해 비교하기 쉽게 한다.
- 단계 종료 시 이 캡처를 실행하고, 사용자가 원본과 나란히 눈으로 확인한다.
- 캡처는 자동 합격·불합격 판정을 하지 않는다.

구현 화면 차이 분류:

- 데이터 차이: 실제 데이터 길이와 값 때문에 발생하는 차이
- 상태 차이: 접근성, 오류, 빈 상태와 로딩 때문에 발생하는 최소 DOM 차이
- 제품 차이: 정보 구조, 문구 또는 상호작용을 바꾸는 차이

원본 파일은 어떤 경우에도 직접 수정하지 않는다. 제품 차이는 사전 승인이 필요하다. 데이터·상태 차이는 시각 영향을 기록하고 스크린샷 확인을 거쳐 구현할 수 있다.

moim-chat.html은 2열 구조를 유지한다. 왼쪽은 개인 AI 대화, 오른쪽은 인터뷰 상태 또는 역할·개인 투두의 검토 영역으로 사용한다. 상태는 `INTERVIEW`(인터뷰·순위 미제출) → `WAITING_ASSIGNMENT`(제출 완료, 다른 팀원 대기와 서버 배정 실행 중) → `ROLE_TODOS`(배정 완료, 내 역할과 투두 초안) 순서로만 바뀌며 이 순서는 승인됨(D-A5)이다. 서버 상태가 바뀌면 접속 중 사용자는 상태 조회로, 미접속 사용자는 재접속 때 다음 화면을 본다. 역할 배정 전에는 오른쪽 투두 영역을 비우고 안내만 표시한다. 각 상태의 세부 문구·집계 표시 범위는 D-B1(B2)이 정했다.

왼쪽 대화와 오른쪽 패널은 서로 다른 임시 상태를 갖지 않는다. 둘 다 같은 서버 측 상태와 revision을 사용하며, 한쪽의 변경은 저장 성공 뒤 다른 쪽에 반영한다.

  2. **보류 시 자동 투표.** REVIEW_NEEDED·NEEDS_INPUT, AI가 읽을 수 없는 형식(HWP·PPTX·XLSX 등), AI 확인 한도 초과, AI 실패, AI 비활성이면 요청 없이 바로 팀원 확인(투표)이 열린다. 그 기록의 AI 결과 한 줄은 **투표 사유로 팀원에게 보인다**(D3 개정: 투표가 열린 시도에 한해 공개 범위 확대). AI 실패는 제출자가 `다시 시도`할 수 있고, 다시 시도하면 투표가 초기화된다.
  3. **과반 기준: 요청자를 뺀 현재 활성 구성원의 과반**(N명이면 `N//2+1` 동의). 요청자는 투표하지 않는다. 동의가 과반이면 완료(`TEAM`), 남은 표를 모두 동의해도 과반이 안 되면 반려(`REJECTED`, 동수는 과반 아님). 나간 팀원의 표는 세지 않고, 나간 뒤 다시 센다. 다른 팀원이 아무도 없으면 본인 제출로 완료(`SELF`). 반려·투표 중에도 같은 할 일에 새 자료를 올릴 수 있으며, 새 시도가 열린 투표를 대신한다(`WITHDRAWN`). 투표 중인 기록의 id만 팀원에게 보낸다.
  4. **그룹 삭제는 그룹장만.** 그룹 화면 ⋯ 메뉴 `그룹 삭제`(그룹장에게만 보임) → 서버가 계산한 영향(팀원 수·기록·첨부 수)을 브라우저 기본 확인창으로 보여 주고, `확인`일 때만 모든 팀원에게서 그룹 전체(대화·역할·할 일·기록·첨부)를 즉시 영구 삭제한다. 다른 팀원은 기존 `그룹 나가기`를 쓴다. D-G1 삭제 기록에 `GROUP_DELETED`를 남겨 복원 뒤 재실행한다.
  5. **대시보드:** 원본의 그룹 카드 진척도·남은 할 일·오늘 마감, `오늘 마감` 알약, `최근 팀 소식`, 오른쪽 패널(주간 날짜·오늘의 할 일·대기 중·그룹 마감)을 실제 데이터로 채운다. 데이터는 각 그룹 화면이 그 사용자에게 이미 보여 주는 범위(D-E1)다. 패널의 할 일은 체크로 완료하지 않고 누르면 그 그룹 화면으로 간다. `대기 중`에는 AI·팀원 확인 중인 내 시도, 기존 패널 스타일로 `팀원 확인 요청`(내 표를 기다리는 다른 팀원의 시도)을 더한다.
  6. **로고:** 로그인 상태 화면(dashboard·group·invite)의 MOIM 로고는 `/dashboard`로 간다(chat·mypage·group-create는 이미 그랬다). 랜딩·로그인·회원가입은 그대로 `/`.
- 이유: 사용자가 "체크 표시를 해서 바로 완료로 넘어가지 말고 업로드를 통한 ai의 판단을 통해서만 완료로 넘어갈 수 있으면 좋을 것", "ai가 거절을 한다면 팀원들이 그것을 확인하여 과반의 동의를 얻으면 거절에서 동의로 넘어갈 수 있도록", 대시보드 오른쪽 바와 최근 팀 소식 구현, 로고 → 대시보드, 내 그룹 삭제를 지시했다.
- 승인 문장(2026-11-20): 위 지시와 세 질문의 답 — 완료 규칙 "보류 시 자동 투표", 과반 기준 "요청자 뺀 팀원의 과반 (Recommended)", 그룹 삭제 "그룹장만 삭제 (Recommended)".
- 위험: AI 보류 사유 한 줄이 팀원에게 보인다(AI 안내 문장은 제출 자료를 요약할 수 있다). 2명 그룹은 상대 1명의 표로 결정된다. 그룹장이 실수로 그룹을 지우면 복구할 수 없다(백업은 장애 복구 전용, D-G1). 기존 수동 완료 기록은 `MANUAL`로 남는다.
