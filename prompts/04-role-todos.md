# 4단계 — 역할 배정 안내, 짧은 인터뷰, 내 투두 만들기·확정

## 목표

`moim-chat` 원본 화면 그대로, 같은 화면 안에서 다음이 이어진다. 팀 전원이 역할 순위를 내면 서버가 역할을 한 번 배정하고, AI가 "당신은 OO 역할이에요(1순위로 배정)"라고 안내한다. AI가 주도해서 그 역할과 프로젝트에 맞는 질문 몇 개(최대 5개, 빠른 답변 버튼 포함)를 하고, 답에 맞춰 그 역할에서만 나올 수 있는 구체적인 내 투두 5개 안팎과 마감일을 오른쪽에 만든다. 사용자는 칸에서 직접 고치거나 "마감을 더 여유 있게 해줘"처럼 AI에게 말해 고치고 `투두 확정하기`를 누른다. 확정된 역할명·투두 제목·마감일만 그룹 구성원이 조회할 수 있고, 인터뷰 내용·순위·숨겨진 평가 기준은 본인과 서버 밖으로 나가지 않는다. 그룹 화면의 투두 렌더링은 5단계다.

원본 화면 구성(고정): 왼쪽 AI 대화(말풍선·빠른 답변·입력창), 오른쪽 `내 투두리스트` 패널(팀 목표 박스 → `내 역할` 줄과 `N순위로 배정` → 투두 줄(체크 칸·제목·마감일·D-n·삭제 ×) → `+ 직접 추가하기` → `투두 확정하기`). 새 디자인·카드·색을 만들지 않는다.

## 선행 게이트

3단계 디자인 눈 확인이 사용자에 의해 완료되어 `docs/ROADMAP.md`·`docs/HANDOFF.md`에 기록돼 있어야 한다. 기록이 없으면 4단계를 시작하지 말고 그 사실만 BLOCKED로 보고한다. GATE B(D-B1)와 D-B3이 승인돼 있고, 아래 `확정 정책`이 `docs/PRODUCT.md`에 승인 결정으로 기록돼 있어야 한다(기록이 없으면 사용자 승인 문장을 받아 기록한 뒤 진행). Timely LIVE 호출은 D-A8(고정 상한 없음, 모든 호출 기록, 단일 작업 100회 이상만 사전 승인)을 따른다. 작업 전 `AGENTS.md`, 활성 문서, 실제 코드를 읽는다.

확정 정책(에이전트 추천안, 사용자 승인 필요):
- 인터뷰: 배정된 역할에 맞춰 AI가 필요한 질문과 빠른 답변 버튼을 만든다. 필수는 `역할 관련 경험`과 `주간 가능 시간`, 도구·선호 시간·일정 제약은 AI가 필요할 때만 묻는다. 최대 5개 질문, 모름 허용, 최대 질문 수에 도달하거나 필수가 UNKNOWN이어도 투두 생성 가능. UNKNOWN 값을 AI·서버가 만들어 채우지 않는다.
- UNKNOWN 주간 시간일 때 업무량은 서버 고정 상한(투두 개수·기간당 분량)으로만 검증한다.
- 일정·환경 제약의 원문은 Timely에 보내지 않는다. 사용자가 확인한 주간 가능 시간·사용 가능 도구·선호 시간·scope로 변환 가능한 정보만 확인 후 반영하고, 날짜·시간 제한은 서버의 결정적 마감일 검증에 사용한다. 변환할 수 없는 제약은 private note로만 보존하며 반영한 척하지 않는다.
- 사용자가 추출 정보를 확인·수정하는 UI는 기존 왼쪽 대화 말풍선·빠른 답변·입력창 안에서만 처리하며 새 카드·패널·화면을 만들지 않는다.
- 그룹 공개 응답은 B7·B9대로 확정된 역할명·투두 제목·마감일 세 가지뿐이다. `task_id`·확정 revision은 서버 내부에 보존하고, 5단계 상호작용에 필요한 불투명 식별자의 노출 방식은 GATE D에서 함께 결정한다.
- 허용 증거 유형은 4단계에서 내부 요구사항과 확장 가능한 enum 구조만 만들고, 실제 업로드 허용 형식은 GATE D 승인 뒤 활성화한다.
- 재배정은 서버 API와 테스트까지만 만든다(화면 없음, 후속 결정).
- ProjectBrief가 바뀌면 D-B1 B8: 후보부터 다시 만들고 기존 확정 투두는 읽기 전용으로 유지한다.
- 한 사용자의 인터뷰 지연·미완료가 다른 사용자의 진행을 막지 않는다.

## 수행

1. 3단계 코드(`interview/ranking.py`, `candidates.py`, `routes.py`, `chat.js`, `chat.html`)와 보존된 `coach.py`·`turns.py`·`e_member_plan`을 읽고 출력 계약을 확인하라. 3단계를 다시 구현하거나 배정 전 인터뷰를 복원하지 마라.
2. cohort 전원이 `WAITING_ASSIGNMENT`가 되면 서버 배정 서비스가 순위 원문을 읽어 1순위 → 2순위 → 3순위 순으로 배정하라. 같은 순위 충돌은 서버 무작위로 한 명을 정하고 탈락자는 다음 순위로 이동한다. 3순위까지 못 받은 사람은 남은 역할 중 서버 무작위로 배정한다. 중복 역할은 역할 수 < 인원일 때만 허용하며(후보 생성은 인원 수 이상을 보장하므로 fixture로만 시험) 구성원별로 결과물을 분할한다. AI는 배정에 관여하지 않는다. 결과는 source cohort와 preference submission revision 집합을 가진 immutable assignment revision 하나로 한 번만 저장하고, 중복 요청·새로고침·재시도로 재추첨하지 않는다. 테스트는 주입 가능한 고정 RNG를 쓰고 운영에서는 조작 가능한 고정 seed를 쓰지 않는다.
3. 배정 성공 뒤 모든 cohort 구성원의 서버 상태를 `ROLE_TODOS`로 바꿔 상태 조회와 재접속에서 같은 assignment revision을 보게 하라. `member_progress`는 `INTERVIEW`·`WAITING_ASSIGNMENT`만 허용하므로 `ROLE_TODOS`와 배정 후 인터뷰 하위 상태를 안전한 마이그레이션으로 추가하라(기존 인터뷰 데이터는 삭제하지 않고, `submission_revision` 보존을 막는 제약은 교체). upgrade·downgrade·upgrade를 확인하라.
4. 배정 직후 서버가 ProjectBrief와 이름 없는 최종 배정표로 내부 팀 coverage(역할별 결과물 분담)를 한 번 고정해 `source_assignment_revision`에 연결하라. 생성은 AI 한 번, 검증은 서버가 ID 수준으로 한다: ProjectBrief의 모든 결과물 항목이 정확히 한 역할(중복 역할이면 한 구성원)에만 매핑되고 누락·중복이 없어야 한다. 실패하면 오류와 명시적 재시도를 보이고 고정 목록으로 대체하지 않는다. 사용자에게 보이는 그룹 계획 화면·엔터티는 만들지 않는다.
5. 왼쪽 대화에서 서버에 고정된 배정 결과를 기존 AI 말풍선 스타일로 먼저 알린다(별도 Timely 호출 없음, AI가 배정을 판단한다는 인상을 주지 않는다)("OO님은 이번 프로젝트에서 ○○ 역할을 맡게 됐어요(N순위로 배정)"). 다른 구성원의 이름·순위·무작위 추첨 결과는 보여주지 않는다(D-B1 B6). 오른쪽 `내 역할` 줄에 역할명과 `N순위로 배정`을 표시한다.
6. 배정 후 인터뷰는 **AI가 주도**한다. 매 턴 Timely가 ProjectBrief, 내 배정 역할, 이름 없는 배정표, 앞선 답변을 보고 "이 역할의 좋은 투두를 만들려면 지금 무엇을 알아야 하는가"를 스스로 판단해 다음 질문과 빠른 답변 버튼 2~4개를 만든다. 질문은 역할마다 달라야 하고(예: 디자인 역할이면 쓰는 도구·시안 경험, 발표 역할이면 발표 경험·자료 제작 방식, 개발 역할이면 언어·배포 경험) 앞선 답에서 이어져야 한다. 고정 질문 목록을 순서대로 나열하지 마라. `coach.py`의 검증·버튼·의미 없는 입력 거절 로직은 재사용하거나 4단계 전용 저장 구조로 ADAPT하되, 기존 `interview_turns`·`member_states`·`member_progress.interview_closed_at`·`InterviewTurnService`는 배정 전 전제라 다시 연결하지 말고 새 session·MemberState·입력 snapshot을 현재 source_assignment_revision에 연결해 저장하라. 정책: 필수는 `역할 관련 경험`과 `주간 가능 시간`, 도구·선호 시간·제약은 AI가 필요할 때만 묻고 최대 5개 질문, 모름 허용, 최대 질문에 도달하면 UNKNOWN이 있어도 투두 생성 가능, UNKNOWN을 AI·서버가 만들어 채우지 않는다. 서버는 사용자 발언 근거, 질문·버튼 유효성, 중복 질문, 의미 없는 입력(저장·질문 수·호출을 소비하지 않음), 완료 조건과 권한을 검증한다. 자유 입력에서 뽑은 정보는 투두 생성 전에 사용자가 확인·수정할 수 있으며, 이 확인·수정은 기존 왼쪽 대화 말풍선·빠른 답변·입력창 안에서만 처리하고 새 카드·패널·화면을 만들지 않는다. 일정·환경 제약은 원문을 공급자에 보내지 않고, 주간 가능 시간·도구·선호 시간·scope로 변환되는 부분만 사용자 확인 뒤 반영하며 변환 불가한 제약은 private note로만 보존한다(날짜·시간 제한은 서버 마감일 검증에 사용). 인터뷰는 배정 역할을 바꾸거나 재배정 근거로 쓰지 않으며 순위 원문은 AI 입력에 넣지 않는다.
7. 인터뷰를 끝낸 사용자부터 자신의 역할 범위 안에서 고정된 coverage에 맞춰 **그 역할에 진짜 맞는 투두**(todo draft)를 생성하라. 투두 품질이 이 단계의 핵심 성공 기준이다. 투두는 다음을 만족해야 한다: (a) 역할의 실제 작업이다. "준비·자료 정리·완성·최종 점검" 같은 어느 역할에도 붙는 일반 제목을 쓰지 않고, 이 프로젝트의 결과물 이름과 구체적 행동이 제목에 드러난다. (b) 내 coverage 결과물을 빠짐없이 덮고 다른 사람의 결과물을 건드리지 않는다. (c) 작업 순서가 맞고(조사·구조 → 초안 → 검토·수정 → 제출) 마감일이 ProjectBrief 기간 안에서 간격을 두고 분포하며 중간 일정(milestones)보다 앞에 온다. (d) 인터뷰에서 알게 된 경험 수준·주간 시간·도구·선호 시간이 분량, 난이도, 순서에 실제로 반영된다(초보자나 시간이 적으면 범위를 줄이고 쪼갠다). 모르는 값은 반영한 척하지 않고 보수적 기본 분량을 쓴다. (e) 개수는 원본 한도 안에서(약 4~8개) 하나가 대략 1~2일 안에 끝낼 크기다. 각 투두는 제목·마감일(화면에 보임)과 내부 `deliverable`, 하나 이상의 구체적이고 확인 가능한 `completion_criteria`, 허용 증거 유형(화면에 안 보임)을 갖고, 모두 `source_assignment_revision`과 입력 snapshot에서 추적된다. 공급자 입력은 D-B1 B3만 허용한다: ProjectBrief, 본인 배정 역할, 이름 없는 최종 배정표, 현재 수준, 주간 가능 시간, scope, 선호 시간, 도구. raw constraints·private notes·순위 원문·대화 원문·다른 구성원 MemberState·이름·아이디·user_id는 보내지 않는다. `E.plan`은 주간 시간·수준이 필수이고 "첫 7일" 정책이라 그대로 쓸 수 없으므로 전용 초안 프롬프트·함수를 새로 만들어 UNKNOWN이어도 생성되게 하라. 서버는 코드로 검증한다: 기간 이탈, 개수, 업무량(UNKNOWN이면 고정 상한), 마감일 순서·간격·milestone 이전 여부, 소유자, coverage 결과물 연결, 비어 있는 결과물·완료 기준, 금지된 일반 제목(예: 제목이 역할명+"준비"/"완성"뿐인 경우). 통과 못 하면 저장하지 않고 오류와 명시적 재시도를 보이며 고정 템플릿 투두로 대체하지 않는다(`F`의 `inspect_plan` 재사용 가능). 프롬프트는 역할별 예시를 섞어 반복 LIVE로 다듬고, 품질은 아래 검증의 기준표로 사람이 판정한다.
8. 오른쪽 패널에서 투두 직접 수정(제목·마감일)·삭제·`+ 직접 추가하기`를 서버 draft에 저장하라(원본의 최대 개수 규칙을 따른다). 같은 대화창의 자연어 수정("마감을 더 여유 있게 해줘")은 AI가 구조화된 변경안(제목·마감일·허용 범위의 추가·삭제)으로만 바꾸고, 서버가 본인 소유·프로젝트 기간·업무량·assignment revision·draft revision을 검증한 뒤 저장한다. 변경안 스키마는 새로 정의한다(`F.revise`는 deliverable·criteria까지 요구하므로 그대로 쓰지 않는다). 수정·추가된 투두는 확정 전에 해당 투두의 숨겨진 `deliverable`·`completion_criteria`·허용 증거를 서버가 다시 생성·검증한다. 재생성이 실패하면 이전 기준으로 확정하거나 고정 기준으로 대체하지 않고 오류와 명시적 재시도를 보이며, 삭제된 투두의 기준은 새 revision에 포함하지 않는다. 배정 역할·담당자는 어떤 경로로도 직접 바꿀 수 없고 AI 변경안에도 포함되지 않는다. 숨겨진 기준을 검토·편집하는 UI는 만들지 않는다.
9. `투두 확정하기`는 보이는 투두와 숨겨진 기준을 같은 불변 revision으로 고정하고 중복 클릭에 멱등이어야 한다. 모든 투두는 생성 때 서버가 안정적인 `task_id`를 부여하며(브라우저·AI가 정하지 않음), 5단계의 첨부·M2 평가가 `task_id`와 확정 revision에 묶이므로 재확정해도 같은 투두는 같은 `task_id`를 유지하고 새로 추가된 투두만 새 `task_id`를 받는다. 허용 증거 유형은 AI가 임의 문자열을 쓰지 못하게 한 곳에서 정의한 확장 가능한 enum에서만 고른다. 4단계는 이 구조와 내부 증거 요구사항만 만들고 실제 업로드 허용 파일 형식은 정하지 않으며, GATE D 승인 뒤에 활성화한다. 확정 뒤 수정은 "확정 풀기 → 수정 → 재확정"으로 새 revision을 만들고 재확정 전까지 이전 확정본이 그룹에 보인다(D-B1 B7). 이미 첨부가 달린 투두의 기준은 첨부가 묶인 이전 revision 그대로 보존하고(새 revision이 이전 revision 기준을 덮어쓰지 않음), 삭제된 투두의 `task_id`는 재사용하지 않는다. 확정 뒤 이동은 기존 그룹 화면으로 한다. 체크 칸은 원본 구조대로 두되 완료 반영은 5단계라 4단계에서는 동작시키지 않는다.
10. 확정된 역할명·투두 제목·마감일 세 가지만 그룹 구성원이 조회하는 서버 API와 직렬화를 만들어라(렌더링은 5단계; `task_id`·revision은 응답에 넣지 않고 서버 내부에만 둔다). private MemberState·조건·순위·숨겨진 기준은 응답·로그·화면에 없어야 한다.
11. 재배정 operation은 그룹장 요청 + 대상자 동의가 있을 때만 새 assignment revision을 만드는 서버 기능과 테스트로 구현하라(화면 없음). 새 revision이 생기거나 ProjectBrief·cohort·preference submission이 바뀌면 D-B1 B8에 따라 관련 draft·확정 투두·숨겨진 기준·역할 맞춤 인터뷰 snapshot·coverage를 STALE 처리하고 현재 입력으로 쓰지 않는다. 역할과 무관한 확인된 시간·도구·선호는 보존할 수 있다.
12. 오른쪽 팀 목표 박스는 2단계에서 최신 ProjectBrief revision으로 만든 표시문과 기간을 읽기 전용으로 표시하고, 이 단계에서 다시 생성하지 않는다. 모든 AI 호출(coverage·인터뷰·투두 초안·자연어 수정)은 서버에서만 하고 브라우저는 Timely나 키를 다루지 않는다. 사용자·AI 출력은 `textContent`/템플릿 이스케이프로만 출력한다.
13. 이번 단계의 인터뷰 항목·최대 5개 질문·종료 조건·확인 UX와 위 확정 정책을 `docs/PRODUCT.md`에 승인 결정으로 기록하고, 변경되는 3단계 경계 테스트(`tests/test_ranking.py`의 assign/todo 금지 검사 등)를 4단계에 맞게 고쳐라. `docs/ARCHITECTURE.md`·`SECURITY.md`·`LIVE_TESTING.md`·`ROADMAP.md`·`HANDOFF.md`를 현재 구현과 일치시키고 5단계는 시작하지 마라.

범위 밖: 별도 개인 목표 단계·엔터티·화면, 평가 기준 검토 UI, 별도 TeamGoal 합성·합의 화면, 그룹 화면의 투두·진행률 렌더링, 그룹 계획 화면, 재배정 화면, 다른 팀원의 private 정보 열람, AI·클라이언트의 임의 배정, 배정 역할·담당자 직접 수정, 외부 캘린더, 원본 HTML 변경, M2 첨부 평가(5단계).

## 검증

- 보안·개인정보: 확정 전 MemberState·인터뷰·순위 원문·draft·숨겨진 기준이 다른 팀원·그룹장·그룹 API·로그·템플릿에 없다. 교차 사용자·교차 그룹·추측 ID·CSRF·XSS를 검사한다.
- 배정: 전원 제출 전에는 assignment·coverage·draft가 생기지 않고, 전원 제출 직후 assignment revision이 정확히 하나 생긴다. 1·2·3순위 반영, 같은 순위 충돌과 다음 순위 이동, 3순위 소진 후 무작위, 중복 역할 fixture의 구성원별 분할, 신규 합류 차단, 재배정의 새 revision과 STALE 전파를 고정 RNG로 검증한다. 중복·새로고침·동시 요청이 재추첨하지 않는다.
- coverage: 팀 필수 결과물에 중복·누락이 없고, 실패는 오류·재시도로 표시되며 대체 목록이 없다.
- 인터뷰: 질문 최대 5개, 필수 2개, 모름·종료 시 막다른 길 없음, UNKNOWN을 만들어 채우지 않음, 의미 없는 입력은 저장·카운트·호출을 소비하지 않음, 한 사용자의 미완료가 다른 사용자를 막지 않음, 재배정 근거로 쓰이지 않음. LIVE에서 서로 다른 역할 3종 이상(예: 기획·디자인·발표·개발 중)으로 실행해 질문이 역할마다 달라지고 앞선 답에서 이어지며 고정 목록의 나열이 아님을 사람이 판정해 기록한다.
- 투두 품질(LIVE, 사람 판정 기준표): 역할 3종 이상 × 경험·시간 조건 2종 이상(초보·시간 적음 / 숙련·시간 많음)으로 생성하고 각 결과를 다음으로 판정해 `docs/LIVE_TESTING.md`에 남긴다. ① 제목이 이 역할·이 프로젝트의 구체적 작업인가(일반 제목 없음) ② 내 결과물을 덮고 남의 것을 침범하지 않는가 ③ 순서와 마감 분포가 자연스럽고 milestone을 지키는가 ④ 수준·시간 조건이 분량과 난이도에 실제로 반영됐는가(두 조건의 결과가 달라야 함) ⑤ 결과물·완료 기준이 구체적이고 확인 가능한가 ⑥ 팀 전체에서 중복·누락이 없는가. 기준을 못 넘으면 프롬프트·검증을 고쳐 다시 LIVE로 확인하고, 통과 못 한 표본과 원인을 숨기지 않는다.
- 투두: 직접 수정·추가·삭제·자연어 수정, 기간 이탈, 과도한 업무량, 교차 사용자 수정, 역할·담당자 변경 차단, revision 충돌, 중복 확정, 저장 실패, 확정 풀기·재확정, 수정·추가 투두의 숨겨진 기준 재생성 실패 시 확정 차단을 검증한다. 각 투두는 비어 있지 않은 결과물·완료 기준·허용 증거를 같은 revision의 숨겨진 snapshot으로 가지며 화면 응답에는 나타나지 않는다.
- 공급자 입력: 각 AI 호출의 요청 본문에 B3 금지 항목이 없음을 fixture 테스트로 확인한다.
- 5단계 인계: 투두마다 서버가 부여한 `task_id`가 확정 revision 사이에서 유지되고 삭제된 `task_id`가 재사용되지 않으며, 허용 증거 유형이 enum 안에 있고, 이전 확정 revision의 숨겨진 기준이 재확정 뒤에도 변하지 않는지 서버 내부에서 검증한다. 그룹 조회 API 응답에는 역할명·제목·마감일 세 가지만 나오고 `task_id`·revision은 나오지 않는지 확인한다.
- 복구: 새로고침·서버 재시작 뒤 상태(ROLE_TODOS, 인터뷰 진행, draft, 확정)가 복구된다. 마이그레이션 upgrade → downgrade → upgrade가 통과하고 기존 인터뷰 데이터가 남는다. 전체 결정적 테스트와 원본 HTML 해시 9개, `prompts/validate-prompts.ps1`이 통과한다.
- Timely LIVE: coverage·인터뷰 턴·투두 초안·자연어 수정 각각의 스키마·완전성을 실제 호출로 검증하고 모든 호출의 call_id·request_id·latency·usage·누적 호출 수를 `docs/LIVE_TESTING.md`에 기록한다. 마지막 AI 프롬프트나 검증 코드를 고친 뒤에는 최종 코드로 LIVE를 다시 실행한다. fixture 결과를 LIVE로 보고하지 않는다.
- 디자인·브라우저: 1440×900 캡처(배정 안내, 인터뷰 중, 투두 초안, 수정 후, 확정 뒤)를 `artifacts/screens`에 저장해 사용자가 원본과 나란히 확인하게 하고, 실제 브라우저에서 순위 제출 → 배정 안내 → 인터뷰 → 투두 → 수정 → 확정 → 새로고침 복구 흐름을 확인한다.

## 중단 조건

3단계 눈 확인 기록이 없거나, 확정 정책 승인이 없거나, 개인정보 공개 범위를 넓혀야 하거나, 원본에 없는 별도 화면(합의·재배정·기준 검토)이 필요하거나, LIVE 권한이 없으면 구현을 추측으로 진행하지 않고 BLOCKED로 보고한다. 범위 밖 기능은 시작하지 않는다.
