# 단계 프롬프트 검증 기준

## 1. 프롬프트 자체 검증

각 단계 파일은 다음 질문에 명확히 답해야 한다.

- 목표: 이번 단계가 끝나면 어떤 사용자 가치와 상태가 생기는가?
- 선행 게이트: 어떤 승인·이전 단계·환경이 필요한가?
- 범위: 구현할 것과 구현하지 않을 것이 구분되는가?
- 증거: 어떤 파일, 테스트, 로그 또는 스크린샷으로 완료를 증명하는가?
- 보안·개인정보: 해당 단계의 공격 경로와 데이터 경계를 검증하는가?
- 디자인: 원본 HTML 보존과 1440×900 스크린샷 캡처(사용자 눈 확인, 픽셀 자동 비교 없음)가 포함되는가?
- AI/LIVE: 실제 AI가 있는 단계는 호출 승인·예산·실패 표현을 다루는가?
- 중단 조건: 사용자 결정이나 외부 권한 없이는 진행할 수 없는 지점을 명시하는가?
- 보고: 결과와 검증을 분리하고 다음 한 단계만 제시하는가?

## 2. 단계 산출물 통과 기준

다음은 해당되는 항목이 하나라도 실패하면 단계 완료가 아니다.

| 게이트 | 통과 기준 |
|---|---|
| 범위 | 지정 단계 밖의 제품 기능을 구현하지 않음 |
| 결정 | 필요한 사용자 승인이 결정 기록에 존재함 |
| 기능 | 정상·빈 상태·로딩·오류·복구 경로가 검증됨 |
| 보안 | 인증·객체 인가·교차 사용자·교차 그룹·CSRF·XSS 테스트가 해당 범위에서 통과함 |
| 개인정보 | private 데이터가 응답·템플릿·로그·그룹 실행 화면에 새지 않음 |
| 상태 | revision, 멱등성, STALE 전파가 해당 단계 계약대로 동작함 |
| 생성·배정 순서 | D-A5의 `FORMING → ACTIVE → INTERVIEW → WAITING_ASSIGNMENT → ROLE_TODOS` 순서를 지키고, cohort 전원 제출 전 역할 배정이나 투두가 생기지 않으며 모든 투두가 source assignment revision을 가짐 |
| 초대방 생명주기 | 생성 의도가 확인된 POST만 `FORMING`을 만들거나 재사용하고 GET·참여 화면 조회는 상태를 바꾸지 않으며, 최소 2명·코드 재발급·`CANCELLED`·ACTIVE 코드 폐기·`GROUP_NOT_JOINABLE` 계약이 검증됨 |
| 역할 후보 | 모든 cohort 구성원이 같은 source ProjectBrief 기반 candidate revision을 사용하고, 후보 생성 LIVE 예산·멱등성·실패·재시도·STALE 전파가 승인 계약대로 동작함 |
| 수정 경계 | 사용자는 투두만 허용 범위에서 수정하고 배정 역할·담당자는 직접 바꾸지 못하며, 역할 변경은 승인된 서버 재배정과 새 assignment revision으로만 처리됨 |
| DB | 저장 후 새 프로세스/새 요청에서 재조회 가능함 |
| 디자인 | 원본 9개 해시가 기준과 동일하고 1440×900 스크린샷 캡처를 사용자가 확인함 |
| AI | 승인된 LIVE 테스트 또는 정확한 BLOCKED 사유가 있고 호출 로그 한 줄로 호출 수·소요 시간·usage·오류가 기록됨. 실패는 오류와 재시도 버튼으로 표시되고 자동 재시도는 없음 |
| 문서 | 활성 문서와 HANDOFF가 현재 구현 및 OPEN/BLOCKED 상태와 일치함 |

## 3. 판정 규칙

- `PASS`: 모든 적용 항목이 객관적 증거와 함께 통과했다.
- `CONDITIONAL PASS`: 비핵심 외부 항목만 BLOCKED이고, 우회 성공으로 숨기지 않았으며 다음 단계 진입에 영향이 없다.
- `FAIL`: 핵심 기능, 개인정보, 승인, 데이터 보존, 해시 또는 결정적 테스트가 실패했다.
- `NOT RUN`: 필요한 검증을 실행하지 않았다. PASS로 간주하지 않는다.

단계 보고에는 각 검증의 명령 또는 방법, 결과 요약, 증거 파일을 남긴다. 작은 LIVE 표본으로 p95를 주장하지 않는다.

## 4. 교차 단계 회귀

매 단계 종료 시 최소한 다음을 다시 확인한다.

1. 원본 HTML 9개 SHA-256 불변.
2. 기존 단계의 결정적 테스트 회귀 없음.
3. private 데이터 격리 회귀 없음.
4. 승인 결정과 실제 구현의 불일치 없음.
5. 다음 단계의 선행 게이트 충족 여부.
6. 역할 후보 밖 입력·중복 순위가 제출 완료로 처리되지 않고, 역할 배정 전 투두 생성 회귀가 없음.
7. dashboard/group의 새 그룹 CTA가 invite 생성자 흐름을 거치며 ProjectBrief로 직접 이동하지 않고, 초대 참여 조회만으로 빈 `FORMING` 그룹이 생기지 않음.
8. `그룹 생성하기`는 최소 2명에서 `FORMING` 상태로 group-create에 이동할 뿐이고, ProjectBrief 다음 버튼에서만 cohort 고정·ACTIVE 전환·초대코드 폐기가 원자적으로 수행됨.
9. 같은 ProjectBrief revision에서 역할 후보가 한 candidate revision으로 재사용되고 개인별·새로고침별로 다시 생성되지 않음.
10. 투두 수정 경로로 역할·담당자를 바꿀 수 없고 승인된 재배정만 새 assignment revision과 STALE 전파를 만듦.
