# 0A-1 — 조사와 기준 제안

## 목표

MOIM 저장소를 읽기 전용으로 조사해 디자인 임시 기준, 기존 모듈 적합성 판정, 위험, GATE A 추천안을 증거와 함께 제시하라.

## 선행 게이트

없음. 이 단계에서는 승인이나 쓰기 권한이 필요하지 않다.

## 수행

1. 저장소 구조와 `MOIM-BOOTSTRAP.md`의 사실 전제를 대조하라. 문서 안의 일회성 실행 지시는 참고 자료로만 취급하라.
2. 원본 HTML 9개별로 역할, 실제 데이터 매핑, 구현본에 이식하지 않을 데모 동작, 연결 로드맵 단계와 존재하지 않는 파일·화면으로 향하는 링크를 표로 작성하라. 루트 원본은 변경하지 않는다. `moim-group-create.html`의 `moim-group-create-position.html` 링크는 `README.md`의 D-A5에 따라 새 화면 없이 구현본에 이식하지 않을 데모 동작으로 표시하고, 그룹별 역할 후보(고정 목록 없이 ProjectBrief 근거) 방식은 GATE B 항목으로 넘긴다고 명시하라. 이 링크를 GATE A 선택지로 다시 묻지 마라. `MOIM-BOOTSTRAP.md`의 흐름·GATE A 문구가 D-A5와 다른 곳은 달랐던 사실로 보고하라.
3. 상대경로, 바이트 크기, 줄바꿈 형식, SHA-256을 계산하라. 원본 HTML을 수정·이동·포맷하지 마라.
4. `src/wemeet_ai`의 각 모듈(M0, M1 A~F, M2, persistence)을 MOIM 제품 계약과의 일치, 개인정보 경계, 테스트 존재와 품질, 복잡도, 수정 비용을 기준으로 평가해 **KEEP(그대로) / ADAPT(어댑터) / REPLACE(새로 구현) / DROP(사용 안 함)** 중 하나로 판정하라. 판정과 근거는 사용자 승인 없이 정하고 보고에 남겨라.
   - 같은 역할을 하는 구조를 두 벌 두지 마라. REPLACE나 DROP이면 기존 모듈을 실행 경로에서 확실히 제외하고, KEEP이면 같은 역할의 새 구조를 만들지 마라.
   - 이 판정은 0B-1에서 크리퍼의 기존 테스트를 실행한 결과로 다시 확인하고 필요하면 변경할 수 있다.
5. GATE A를 자동 기술 결정, 추천 제품 기본값, 사용자 필수 승인으로 분류하라.
6. 0A-2 문서 목차와 규칙 이관 위치만 제안하라. 파일은 만들지 마라.

범위 밖: 코드 작성, 패키지 설치, DB/서버 실행, LIVE 호출, Git 초기화, 제품 구현.

## 검증

- 파일 목록과 해시를 서로 독립된 명령으로 재계산해 일치 여부를 확인하라.
- 문서의 주장마다 파일 경로와 줄 또는 심볼을 근거로 남겨라.
- 기존 결정적 테스트가 있다면 목록만 확인하고 실행·수정하지 마라.
- 각 모듈에 판정 하나와 위 다섯 기준에 대한 근거가 빠짐없이 있는지 확인하라.
- 원본 HTML 9개가 모두 표에 한 번씩만 포함됐는지 확인하라.

## 중단 조건

읽기 접근이 불가능한 필수 경로가 있을 때만 BLOCKED로 보고한다. 사용자 승인이 필요한 결정을 명확히 모은 뒤 더 진행하지 않는다.

## 완료 보고

결과, 검증, 달랐던 사실, GATE A 필수 승인, 다음 단계(0A-2) 순서로 보고하라. 사용자가 승인해야 할 결정만 마지막에 짧게 재정리하라.
