# 0B-2 — M0 안정화와 Timely LIVE 연결

## 목표

공급자 요청의 개인정보 로그 위험과 자동 재호출을 결정적 테스트로 먼저 제거하고, 승인된 최대 12회 예산 안에서 Timely 실제 연결과 구조화 응답을 검증한다. MVP에서는 실패 처리를 단순하게 유지한다. 자동 재시도·UNKNOWN 분류·자동 JSON 복구 호출은 만들지 않고, 실패하면 오류를 저장해 사용자에게 재시도 버튼을 보여준다.

## 선행 게이트

0B-1이 통과해야 한다. 결정적 안정화에는 LIVE 승인이나 API 키가 필요하지 않다. LIVE 확인에만 사용자 승인, 예산과 서버 측 자격증명이 필요하다.

## 수행

1. `provider.request`, `provider.response`, `json.parsed`를 포함한 전체 provider 경로에서 body/messages, AI 응답 원문·파싱 결과 원문, API 키, private 원문이 로그에 남지 않게 수정하라. 모델, 스키마명, 크기·개수, 안전한 해시, request/call ID, latency, usage, 상태와 오류 코드만 기록하라.
2. 기존 코드의 자동 재호출과 자동 JSON 복구 호출을 제거하라. 타임아웃, 429/5xx, JSON/스키마 오류는 모두 실패로 반환하고, 호출한 쪽이 오류를 저장해 사용자에게 재시도 버튼을 보여줄 수 있게 하라.
3. 실제 Timely 호출마다 단계, 모델, 성공·실패, 소요 시간, usage를 로그 한 줄로 남겨 호출 횟수를 셀 수 있게 하라. 구간별 지연 측정과 attempt별 예산 예약은 만들지 마라.
4. 사용자가 재시도를 누르면 새 호출로 처리하라. 시간 초과 뒤 재시도로 같은 요청이 두 번 과금될 수 있음은 MVP에서 감수한다.
5. 결정적 fixture 테스트를 먼저 통과시키고 공급자 호출·실패 계약을 짧게 문서화해 `DETERMINISTIC PASS` 여부를 판정하라.
6. LIVE 승인·예산·자격증명이 있으면 정상 text와 정상 structured output을 검증해 별도의 `LIVE PASS` 여부를 판정하라. 없으면 `LIVE BLOCKED`로 기록하되 결정적 부분을 실패로 바꾸지 마라.
7. Timely 실패를 다른 공급자나 고정 성공 응답으로 숨기지 마라.

범위 밖: 자동 재시도·UNKNOWN 분류·backoff·자동 JSON 복구, 구간별 지연 측정, 사용자용 AI 화면, 여러 모듈 연쇄 호출, worker/queue 구현, 예산 초과 호출, 원본 HTML 변경.

## 검증

- 로그 캡처로 요청 원문, AI 응답 원문, 파싱 결과 원문과 키가 모든 성공·오류 이벤트에 없음을 확인하라.
- 타임아웃, 429/5xx, JSON/스키마 오류가 자동 재호출 없이 실패로 반환되는지 결정적 테스트로 검증하라.
- 사용자 메시지 한 번이 실제 HTTP 호출 한 번만 만드는지 확인하라.
- 각 LIVE 호출을 성공 여부와 무관하게 예산에 포함하고 호출 로그 한 줄이 남는지 확인하라.
- 기존 결정적 테스트와 원본 HTML 해시 검사를 실행하라.

## 중단 조건

결정적 안정화가 실패하면 다음 기반 단계로 진행하지 않는다. LIVE 승인·키·네트워크가 없으면 LIVE 부분만 BLOCKED로 보고하며 0B-3과 1단계는 진행할 수 있다. 단, 3단계 진입 전에는 LIVE 확인을 완료해야 한다. 12회 초과가 필요하면 실패 증거, 추가 검증 항목과 필요한 횟수를 보고하고 승인을 요청한 뒤 멈춘다.

## 완료 보고

안정화 결과를 `DETERMINISTIC PASS/FAIL`과 `LIVE PASS/BLOCKED/FAIL`로 분리해 보고하고, 실제 호출 수와 잔여 예산, 다음 한 단계(0B-3)를 명시하라.
