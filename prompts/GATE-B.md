# GATE B — 인터뷰·공유 정책 추천안

## 목표

2단계까지의 실제 코드와 디자인을 읽기 전용으로 조사해 D-A5로 이미 승인된 비동기 제출 장벽과 서버 역할 배정 순서를 유지하면서, 3·4단계에 아직 필요한 제품·개인정보 결정만 쉬운 추천안으로 만들고 사용자 승인만 요청한다.

## 선행 게이트

2단계가 검증을 통과하고 현재 데이터 모델, `moim-chat.html`, 관련 활성 문서를 읽을 수 있어야 한다.

## 수행

1. 인터뷰 필수 항목, 최대 턴, 종료·재개 조건의 추천값을 근거와 함께 제시하라.
2. 승인된 `INTERVIEW → WAITING_ASSIGNMENT → ROLE_TODOS` 전환을 원본 `moim-chat` 2열에서 표현할 세부 문구, 재개·오류 상태와 집계 표시 범위를 추천하라. 순위 미제출, 제출 완료 뒤 대기(예: `3/5명 제출 완료`), 서버 배정 실행 중(예: `역할을 배정하고 있어요`), 배정 완료 뒤 내 역할·투두 초안 표시의 네 화면 상태를 모두 포함하라. 역할 배정 전 투두 패널과 `투두 확정하기`는 비어 있거나 비활성 상태여야 하며, 패널에 표시할 안내 문구도 추천하라.
3. private MemberState에서 역할 후보·선호 검증과 최종 역할 뒤 투두 초안에 사용할 수 있는 최소 필드, 공급자에게 보내지 않을 필드를 구분해 제시하라.
4. D-A5의 활성화 cohort 전원 유효 제출 뒤 서버 배정 원칙을 전제로, 미제출자 처리, 2단계에서 차단한 활성화 뒤 신규 합류의 허용 여부·cohort 편입 방식과 재배정 조건을 추천하라. 후보에 존재하는 서로 다른 역할 ID 세 개만 제출 완료로 인정한다. 각 순위의 같은 역할 충돌은 서버 무작위로 한 명을 정하고 탈락자는 다음 순위로 이동하며, 3순위까지 배정되지 않은 구성원은 남은 역할 중 서버 무작위로 배정한다. 남은 역할이 없을 때의 중복 허용과 팀 전체 deliverable 기준 투두 분할 규칙도 추천하라. 개인의 순위 원문은 배정 서비스만 사용하고 다른 구성원·그룹장에게 공개하지 않는 것을 기본으로 한다.
5. D-A5에 따라 포지션 등록 화면은 없으므로, 고정 목록 없이 ProjectBrief를 근거로 그룹별 역할 후보를 만드는 생성 주체·시점·개수·표시 위치를 추천하라. 모든 cohort 구성원이 `source_project_brief_revision`을 가진 하나의 immutable candidate revision을 함께 사용하고 개인 인터뷰마다 후보를 다시 만들지 않게 하라. AI를 사용한다면 ProjectBrief revision당 최초 생성과 사용자 명시적 재시도 횟수를 포함한 별도 LIVE 예산, 실패 표시, 멱등성, 새로고침 복구와 ProjectBrief 변경 시 STALE 규칙을 추천하라. 승인된 candidate revision이 없으면 역할 순위 제출을 시작하지 않는 것을 기본으로 한다.
6. 랜덤 배정 안내 문구에서 다른 구성원의 이름·순위를 보여줄지 추천하라. 원본 `moim-chat` 데모 문구는 이를 노출하므로, 순위 비공개를 유지하려면 이름을 뺀 문구를 제품 차이로 승인받아야 한다.
7. 최종 assignment revision 뒤 생성된 개인 투두를 사용자가 확정하기 전과 후의 그룹 공개 범위와 수정·재확정 규칙을 추천하라. 사용자가 직접 수정할 수 있는 것은 투두 제목·마감일·허용 범위의 추가·삭제로 제한하고, 배정 역할 변경은 별도 승인된 서버 재배정 operation으로만 수행하며 새 assignment revision과 기존 draft/confirmed assignment의 STALE 처리를 동반하게 하라. 역할 배정 전 투두 생성이나 브라우저의 역할 문자열 직접 변경은 선택지로 제시하지 마라.
8. ProjectBrief 또는 assignment revision 변경 시 이전 투두 draft/confirmed assignment와 숨겨진 평가 기준의 STALE·재검토 조건을 추천하라.
9. 각 항목마다 추천안, 사용자 관점의 장점, 위험, 영향을 짧게 설명하고 승인 여부만 질문하라.

범위 밖: 코드·DB 변경, 사용자 승인 전 문서 변경, Timely LIVE 호출, 3·4단계 구현, 원본 HTML 변경. 승인 후 결정 기록에 필요한 운영 문서만 변경할 수 있다.

## 검증

- 그룹에 공개되는 확정 정보가 private conversation/profile 원문을 포함하지 않는지 데이터 흐름으로 확인하라.
- 추천 상태 전환이 원본 HTML 2열 구조와 동일 서버 revision 원칙을 지키는지 확인하라.
- 서버 무작위 배정이 순위 선호를 건너뛰지 않고, 같은 입력·배정 revision 안에서 중복 실행이나 새로고침으로 다시 추첨되지 않도록 멱등·감사 경계를 확인하라.
- 역할 후보 밖 문자열·중복 순위가 제출 완료로 처리되지 않고, cohort 전원 제출 전에는 assignment나 todo draft가 만들어지지 않으며, 모든 todo draft가 source assignment revision을 가지는지 데이터 흐름으로 확인하라.
- 역할 후보 생성이 모든 cohort 구성원에게 같은 candidate revision을 제공하고, source ProjectBrief revision·호출 예산·실패·재시도·STALE 경계를 빠짐없이 다루는지 확인하라.
- 사용자 투두 수정과 서버 역할 재배정의 권한·revision 경계가 분리되고 역할 문자열 직접 수정 경로가 없는지 확인하라.
- 기존 결정적 테스트와 계약에서 충돌하는 가정을 찾아 명시하라. 테스트를 수정하지 마라.
- 모든 GATE B OPEN 항목과 역할 후보 방식·배정 안내 노출 범위·미제출·신규 합류·재배정·중복 역할의 투두 분할·확정 규칙이 승인 질문에 포함됐는지 점검하라. D-A5로 확정된 순서를 다시 선택지로 묻지 마라.

## 중단 조건

실제 데이터 계약을 읽을 수 없거나 개인정보 공개 범위를 판단할 근거가 없으면 추측하지 말고 BLOCKED로 보고한다.

## 완료 보고

추천안 표, 근거, 위험, 사용자 승인이 필요한 결정만 제시하고 승인을 기다려라. 기술 구현 선택은 질문하지 마라. 사용자가 승인하면 같은 작업에서 `docs/PRODUCT.md`의 사용자 승인 결정 기록에 결정 ID, 날짜, 사용자의 승인 문장과 영향 단계를 남기고, `docs/ROADMAP.md`의 해당 OPEN 항목을 승인 결과로 갱신하며, `docs/HANDOFF.md`를 현재 상태와 다음 한 단계로 갱신하라. 문서 외 파일은 변경하지 않는다.
