# 0B-3 — AI 작업 상태 저장과 화면 캡처 기반

## 목표

AI 작업을 FastAPI 백그라운드 작업으로 실행하고 DB에 상태를 저장해 새로고침 뒤에도 복구하는 기반과 원본·구현 화면을 1440×900으로 나란히 캡처하는 스크립트를 만든다.

## 선행 게이트

0B-1 기반과 0B-2의 결정적 부분이 통과(`DETERMINISTIC PASS`)했고 공급자 상태 계약이 문서화돼 있어야 한다. 0B-2 LIVE 확인은 BLOCKED 상태여도 진행할 수 있다.

## 수행

1. AI 작업 상태(대기·진행·완료·실패)와 operation ID, revision, 결과를 저장하는 PostgreSQL 테이블을 만들고 FastAPI 백그라운드 작업으로 실행하라. 별도 worker 프로세스, lease, crash 모델링은 만들지 마라.
2. API는 입력 저장 후 빠르게 202와 상태 URL을 반환하고, 화면은 상태를 주기적으로 조회해 새로고침 후에도 상태와 결과를 복구하게 하라.
3. 서버 시작 시 진행 중으로 남은 작업은 실패로 표시하고 재시도할 수 있게 하라. 같은 operation의 중복 요청은 새 작업을 만들지 않게 하라.
4. Playwright 스크립트 하나로 원본 HTML 9개와 대응하는 구현 화면을 1440×900에서 캡처해 나란히 볼 수 있게 저장하라. 개발 seed는 적용하되 픽셀 자동 비교, 기준 이미지, 허용 오차, 날짜·폰트 고정과 마스킹은 만들지 마라.
5. 원본 HTML과 구현 화면을 분리하고 원본은 읽기 전용으로 유지하라.

범위 밖: 별도 worker 프로세스·lease·crash 모델링, 픽셀 단위 자동 비교·허용 오차, 제품 단계 UI 완성, 신규 큐 의존성, 무제한 retry, 모바일 신규 설계, 원본 HTML 변경.

## 검증

- 작업 중 서버 재시작 뒤 실패 표시와 재시도, 중복 요청, revision 충돌, 새로고침 복구를 결정적 테스트로 검증하라.
- 실제 DB 재조회로 프로세스 메모리 의존이 없음을 확인하라.
- 캡처 스크립트가 한 명령으로 실행되고 원본·구현 스크린샷 쌍을 저장하는지 확인하라.
- 원본 HTML 해시와 전체 결정적 테스트를 실행하라.

## 중단 조건

Redis/Celery/RQ 등 주요 의존성이 실제로 필요하면 근거와 대안을 제시하고 승인 전에 중단해 BLOCKED로 보고한다. 제품 차이가 필요한 시각 변경도 중단한다.
