# GATE D — 파일·검토·생명주기 정책 추천안

## 목표

4단계까지의 실제 상태를 읽기 전용으로 조사하고, 가능한 경우 승인된 사전 예산으로 vision 지원을 확인한 뒤 5·6단계의 검토·파일·탈퇴 정책 추천안을 만들어 사용자 승인만 요청한다. vision을 확인할 수 없어도 M2.review만 비활성화하고 나머지 추천과 단계 진행은 막지 않는다.

## 선행 게이트

4단계와 GATE B 결정이 검증을 통과해야 한다. Timely vision 사전 확인은 LIVE 승인, 자격증명과 최대 3회 예산이 있을 때만 수행한다.

## 수행

1. LIVE 승인·자격증명·예산이 있으면 코드 변경 전에 고정된 비민감 fixture로 Timely vision과 승인 후보 파일 유형의 처리 가능성을 합계 최대 3회 확인하고 각 request ID, 모델, latency, usage, 오류를 기록하라. 하나라도 없으면 호출하지 말고 `LIVE BLOCKED`로 기록하라.
2. vision 지원이 확인된 경우에만 `M2.review` 입력을 특정 투두의 확정 snapshot으로 제한하라: 투두 제목, 내부 `deliverable`·`completion_criteria`, 허용 증거와 그 투두에 첨부된 자료. MemberState·전체 private 대화·profile, 다른 투두나 구성원의 데이터는 보내지 마라. M2가 기준을 수정하거나 프로젝트 전체 완료를 판단하지 못하게 하라. vision을 확인하지 못하면 M2.review 비활성화를 추천하되 일반 투두 완료·파일 제출·수동 확인은 계속 진행하게 하라.
3. M2 활성 시 원본의 `첨부하면 이 할 일을 완료로 표시` 체크박스를 그대로 수동 완료로 둘지, M2 제출 동의로 해석할지, PASS 뒤에만 완료로 반영할지 추천하라. 의미가 바뀌면 제품 차이로 명시하고 사용자 승인을 요청하라.
4. `PASS`·`REVIEW_NEEDED`·`NEEDS_INPUT` 결과와 보완 안내·이의 제기를 어디에 어떻게 표시할지 추천하라. 새 패널을 기본으로 추가하지 말고 기존 업로드 결과 안내 줄 `up-msg`와 `팀원 완료 기록`을 우선 재사용하며, 공개 범위와 문구를 함께 제시하라.
5. 이미지·PDF·DOCX 허용 범위와 형식·크기·개수 제한을 추천하라.
6. 첨부파일의 보관 기간, 접근, 삭제, 계정/그룹 탈퇴 시 처리 방식을 추천하라.
7. 그룹 탈퇴, 마지막 그룹장, 계정 삭제·익명화·법적/운영 보관 정책을 추천하라.
8. 각 항목의 추천안, 장점, 개인정보·비용·디자인·복구 위험을 설명하고 승인 여부만 질문하라.

범위 밖: 제품 코드·DB 변경, 사용자 승인 전 결정 문서 변경, 실제 사용자 파일 전송, M2.review 실행, 5·6단계 구현, 원본 HTML 변경. vision 사전 확인 결과는 `docs/LIVE_TESTING.md`와 `docs/HANDOFF.md`에 기록할 수 있고, 승인 후에는 결정 기록에 필요한 운영 문서만 변경할 수 있다.

## 검증

- vision LIVE 호출은 각 시도를 성공·실패와 무관하게 1회 예산으로 세고 합계 3회를 넘지 않으며, 민감정보·data URL이 로그에 없는지 확인하라.
- LIVE 권한이 없으면 결정적 테스트 fixture로 요청 생성·로그 차단까지만 확인하고 vision 결과는 `LIVE BLOCKED`로 표시하라.
- M2 입력이 제출한 구성원의 해당 투두 snapshot과 첨부 자료로만 제한되고, MemberState·다른 투두·대화가 포함되지 않는지 확인하라.
- 체크박스 의미, M2 결과·보완 안내·이의 제기 표시가 원본에 없는 동작임을 제품 차이로 분류하고, `up-msg`와 팀원 완료 기록을 재사용하는 추천이 별도 새 화면보다 우선됐는지 확인하라.
- 삭제·익명화·보관 추천을 계정, 그룹, 산출물, 첨부별로 대입해 충돌과 복구 불가능성을 확인하라.
- 원본 HTML의 제품 차이를 요구하는 추천이 없는지 확인하라.

## 중단 조건

vision 결과를 확인하지 못하면 M2.review만 `BLOCKED/비활성`로 두고 파일·제출·생명주기 추천은 계속한다. 개인정보 보관 근거가 불명확하면 해당 파일·삭제 정책의 승인 요청 전에 중단한다.

## 완료 보고

vision 사전 확인을 수행했거나 `LIVE BLOCKED`를 판정한 직후 호출 수, 모델, 지원 여부, latency, usage와 오류를 `docs/LIVE_TESTING.md`에 기록하고 `docs/HANDOFF.md`에 M2 활성/비활성 상태와 GATE D 대기 상태를 갱신하라. 추천안 표, 위험, 사용자 승인이 필요한 결정만 제시하고 승인을 기다려라. M2 LIVE 예산은 사용하지 마라. 사용자가 승인하면 같은 작업에서 `docs/PRODUCT.md`의 사용자 승인 결정 기록에 결정 ID, 날짜, 사용자의 승인 문장과 영향 단계를 남기고, `docs/ROADMAP.md`의 해당 OPEN 항목을 승인 결과로 갱신하며, `docs/HANDOFF.md`를 현재 상태와 다음 한 단계로 다시 갱신하라. 문서 외 파일은 변경하지 않는다.
