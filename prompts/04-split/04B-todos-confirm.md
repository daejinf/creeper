# 04 세션 B — 투두 초안, 수정, 확정, 그룹 조회 API (수행 7~10)

주 실행 프롬프트는 `prompts/04-role-todos.md`다. 이 파일은 그 프롬프트의 수행·검증 절을 세션별로 나눈 것이며 내용을 바꾸거나 완화하지 않는다. 충돌하면 `prompts/04-role-todos.md`, `AGENTS.md`가 우선한다. 4단계는 세션 C가 끝나기 전까지 완료가 아니다. 5단계는 시작하지 않는다.

## 공통 규칙 (세션 A·B·C 동일)

- 새 세션에서 시작한다. 이전 맥락은 대화가 아니라 `docs/HANDOFF.md`와 활성 문서에서 이어받는다. 작업 전 `AGENTS.md`, `prompts/README.md`, `prompts/VALIDATION.md`, `docs/HANDOFF.md`, `docs/PRODUCT.md`(D-B1·D-B3·D-B4), 실제 코드를 읽는다. 문서와 코드가 다르면 실제 코드를 근거로 보고한다.
- 선행 게이트를 확인한다: 3단계 완료 기록, D-B4 승인 기록, **HANDOFF에 `세션 A 완료` 기록**. 하나라도 없으면 BLOCKED로 그 사실만 보고한다.
- 03 프롬프트와 이전 보정 프롬프트는 쓰지 않는다. 3단계를 다시 구현하거나 배정 전 인터뷰를 복원하지 않는다.
- 원본 HTML 9개, `prompts/04-role-todos.md`, `AGENTS.md` 헌법 영역, PRODUCT.md의 기존 승인 결정을 수정하지 않는다.
- 반복 실행에는 변경과 관련된 테스트만 돌린다. 전체 결정적 테스트와 교차 단계 회귀는 세션 C가 단계 종료 때 한 번 실행한다.
- LIVE 호출은 D-A8을 따른다. 모든 호출의 call_id·request_id·latency·usage와 누적 호출 수를 `docs/LIVE_TESTING.md`에 기록하고 fixture를 LIVE로 보고하지 않는다. 누적이 단일 작업 100회에 가까워지면 멈추고 사전 승인을 받는다.
- 세션 종료 시 `docs/HANDOFF.md`를 현재 상태로 갱신한다. `4단계 진행` 절에 이번 세션의 완료 범위, 만든 파일·테이블·API, 다음 세션이 알아야 할 사실, 남은 OPEN을 적는다. ROADMAP.md에서 4단계를 완료로 바꾸지 않는다.
- 커밋하지 않는다. 사용자가 확인한 뒤 커밋한다.
- 마지막 보고는 `결과 / 검증 / 달랐던 사실 / OPEN·BLOCKED / 다음 한 단계` 순서이며 빈 항목은 채우지 않는다.
- 중단 조건(04 프롬프트 `중단 조건`)에 해당하면 추측으로 진행하지 않고 BLOCKED로 보고한다. 같은 원인의 실패가 3회 반복되면 같은 시도를 멈추고 시도·공통 원인·대안·필요한 조치를 보고한다.
- 수행 12(서버에서만 AI 호출, 브라우저는 Timely·키를 다루지 않음, 출력은 `textContent`/템플릿 이스케이프만, 오른쪽 팀 목표 박스는 2단계 표시문을 읽기 전용으로 표시)는 모든 세션의 공통 제약이다.
- 3단계의 "배정·투두 금지" 경계 테스트가 이번 세션의 변경으로 실패하면, 그 테스트만 4단계 계약에 맞게 고치고 무엇을 왜 고쳤는지 HANDOFF에 남긴다(검증을 약화하지 않는다).

## 이 세션의 범위

`prompts/04-role-todos.md` 수행 **7~10**만 한다.

7. 인터뷰를 끝낸 사용자부터 고정된 coverage의 본인 역할 범위 안에서 **역할에 진짜 맞는 투두 초안** 생성(품질 기준 (a)~(e), 숨겨진 `deliverable`·`completion_criteria`·허용 증거, B3 입력만, 전용 초안 프롬프트·함수, 서버 코드 검증, 실패는 오류·명시적 재시도, 템플릿 대체 없음).
8. 직접 수정·삭제·추가와 자연어 수정(새 구조화 변경안 스키마). 수정·추가된 투두의 숨겨진 기준은 확정 전에 다시 생성·검증하고, 실패하면 확정을 막는다.
9. `투두 확정하기`: 보이는 투두와 숨겨진 기준을 같은 불변 revision으로 고정, 멱등, 서버 부여 `task_id` 유지·삭제 ID 비재사용, 확정 풀기→수정→재확정 새 revision, 첨부가 묶인 이전 revision 기준 보존, 허용 증거 유형은 확장 가능한 enum 구조만(업로드 허용 형식은 GATE D 뒤).
10. 확정된 역할명·투두 제목·마감일 세 가지만 그룹 구성원이 조회하는 API(`task_id`·revision 미노출, 렌더링은 5단계).

하지 않는 것: 재배정·STALE 처리(수행 11), 최종 문서 정리(13), M2 첨부 평가·그룹 화면 투두 렌더링(5단계).

## 이 세션에서 지킬 설계 조건

- 모든 투두·숨겨진 기준·초안·확정 revision은 `source_assignment_revision`과 입력 snapshot에 연결해 저장하라. 세션 C가 재배정·ProjectBrief 변경 때 이를 STALE로 표시할 수 있어야 한다.
- 이 단계에서 가장 중요한 성공 기준은 투두 품질이다. 04 프롬프트 `검증`의 투두 품질 기준표(①~⑥)로 역할 3종 이상 × 조건 2종 이상을 LIVE로 생성해 사람이 판정할 수 있게 `docs/LIVE_TESTING.md`에 남기고, 기준을 못 넘으면 프롬프트·검증을 고쳐 다시 LIVE로 확인하라. 통과 못 한 표본과 원인을 숨기지 마라.

## 이 세션의 검증 (04 프롬프트 `검증` 절 중)

투두(수정·추가·삭제·자연어·기간 이탈·업무량·교차 사용자·역할 변경 차단·revision 충돌·중복 확정·저장 실패·확정 풀기/재확정·기준 재생성 실패 시 확정 차단), 투두 품질(LIVE 기준표), 공급자 입력(초안·수정 호출에 B3 금지 항목 없음), 5단계 인계(`task_id` 유지·재사용 금지·enum·이전 revision 기준 불변·그룹 API 세 필드만), 보안·개인정보(투두 범위), 복구(draft·확정 새로고침·재시작), Timely LIVE(초안·자연어 수정).
